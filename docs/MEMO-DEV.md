- **adb et SuperDisplay** : le service Windows SuperDisplay fait tourner son propre adb (1.0.40, `C:\Program Files\SuperDisplay\adb\adb.exe`) et le relance sans cesse. ## Règles propres à chaque domaine

- **Commandes natives** (`src-tauri/src/data.rs`) : les fenêtres de fichier s'ouvrent côté Rust, l'interface ne transmet jamais de chemin.
- **Appli Android** (V2, étape 10) : le même Rust, ce qui n'existe que sur le PC est marqué `#[cfg(desktop)]` (modules `data`, `notion`, `now`, `presence`, plugins de bureau) ; deux listes de commandes dans `lib.rs`, une par plateforme. Les dépendances de bureau sont dans `[target.'cfg(not(any(target_os = "android", target_os = "ios")))'.dependencies]` du `Cargo.toml`. Secrets par `vault.rs` (jamais `keyring` directement). Le téléphone reçoit Google et la clé par le code QR du PC (`link.rs`, `PhoneLink.tsx`). Le projet Android (`src-tauri/gen/android`) est versionné ; construire et installer : [android.md](android.md). **Écrans** : le téléphone reprend les pages du PC (routeur `src/mobile/router.tsx`, mêmes chemins) ; les adapter par la variante `phone:` (CSS, posée par `main.tsx`), ou `isMobileApp()` pour rendre autre chose, jamais en changeant le PC. Une page reprise qui ouvre une fenêtre a besoin d'elle dans `MobileOverlays.tsx` ; un lien vers une page absente du téléphone doit y avoir une route (ou ne pas s'afficher). Pont natif : `window.CockpitAndroid` (`MainActivity.kt`). Les onglets et le glissement entre eux sont dans `MobileShell.tsx` (un élément peut l'empêcher avec `data-no-swipe`) ; l'icône Android se redessine par `scripts/android_icons.py`.
- **Google** (`src-tauri/src/google.rs`, `src/domains/google/`) : réseau, OAuth et jetons côté Rust seulement, l'interface ne fait aucun appel réseau. Identifiants du client et jeton dans le Gestionnaire d'identification de Windows, **jamais** dans la base, les exports ou le dépôt (public). Les événements sont une copie locale en lecture seule (`google_events`), non exportée, source `google` de l'agenda.
- **Événements récurrents** (P15) : la règle (RRULE) est stockée une fois dans `events.recurrence`, les occurrences sont calculées (`agenda/recurrence.ts`), seules les exceptions sont stockées (`event_exceptions`). Tout ce qui lit des événements passe par ces occurrences (`listAgenda`, `listRecurringOccurrences`).
- **Deux fenêtres** : la principale (`index.html`) et la mini-fenêtre « En ce moment » (`now.html`, `src/now.tsx`, `src-tauri/src/now.rs`), volontairement sans routeur ni cache. Elle écrit par le même pont SQLite et prévient la principale par un événement natif (`cockpit:data-changed`). (La capture rapide et sa fenêtre ont été retirées le 26/11/2026, avec la boîte de réception.)
- **Modes** (P13) : `app/modes.ts` dit à quel mode appartient une page ; `NAV` (`app/navigation.ts`) donne la barre latérale de chaque mode. Une vue d'un seul mode trie avec `tasksOfMode` (tâches) ou `isSchoolItem` (agenda). L'espace Cours est dans `src/domains/school/` (matières, périodes, emploi du temps, examens, notes, devoirs) ; un devoir est une tâche avec `subject_id`, et, s'il est à rendre pour un cours précis de Google, avec `course_event` ('agenda|événement').
- **Journée** (P16-P18) : `src/domains/day/`. Un bloc porte sa date ; une tâche dans un bloc (`tasks.block_id`) prend le jour du bloc via `blockDate` (jointure), jamais recopié. Les heures des blocs sont 'HH:MM', '24:00' pour minuit.
- **Pages** (P19) : `src/domains/pages/`. Le schéma des blocs (`editor/nodes.ts`) sert à l'éditeur et au Markdown (`editor/markdown.ts`, testable sans navigateur) ; les vues React sont dans `editor/extensions.ts`. Images dans la table `attachments` (data URL), référencées par `attachment:<id>`. **Lignes transformées** (ce que faisait la boîte de réception) : un clic droit sur une ligne en fait une tâche, un devoir, un événement, une idée ou un projet (`editor/page-lines.ts` pour les règles, `LineMenu.tsx`, `line-actions.ts`) ; les fenêtres de création reçoivent `fromLine` (`app/create-store.ts`) et appellent `onCreated` au lieu de leur toast. `line-actions.ts` et `page-lines.ts` tirent le schéma de l'éditeur : jamais depuis `pages/hooks.ts` (barre latérale). **Poignées** « + » et « ⠿ » à gauche des blocs : `editor/BlockGutter.tsx` (affichage, glisser par `view.dragging`) et `editor/block-handle.ts` (règles).
- **Couleurs** : une couleur choisie est un `AppColor` : une clé de la palette (`'blue'`…, adaptée au thème) ou une couleur libre `'#rrggbb'`. Tout rendu passe par `colorVar()` (`ui/data/ColorDot.tsx`), jamais `var(--p-…)` écrit à la main ; le choix par `ColorChoice` (palette + « Autre couleur ») ou `ColorButton` (pastille d'une ligne). Un projet a sa couleur, sinon celle de son type (`COALESCE(p.color, pt.color)` dans les requêtes).
- **Cours venant de Google** : l'agenda des cours se **reconnaît seul** à la relecture (`looksLikeTimetable` : intitulés « Matière | Type | Prof », ou `isTimetableName` : un nom comme « Emploi du temps »), tant qu'aucun agenda n'en est un et que le réglage `google.schoolManual` (choix fait à la main dans Paramètres) n'existe pas. `parseCourseTitle()` lit la matière, le type (« Cours », « Examen »…) et les profs (`google_events.course`, `course_kind`, `teacher`) ; `course_links` relie chaque intitulé à une matière, **créée toute seule** à la relecture, ou l'ignore (`subject_id` NULL). Les matières se créent seules ; la page Matières (en fin de barre du mode Cours) sert à les gérer. Un cours s'affiche sous le nom de sa matière (`COALESCE(s.name, g.course)`), qui suit donc un renommage ; supprimer une matière fait de ses intitulés des « pas un cours » (`ON DELETE SET NULL`, ils ne reviennent pas à la relecture), et « Annuler » les lui rend (`SubjectSnapshot.courses`). Dans l'agenda, un cours est un élément `source 'google'`, `kind 'class'`, avec `subjectId`, titré par son nom propre ; il appartient au mode Cours (`isSchoolItem`) : absent du dashboard Travail, dans « Cours du jour » et « Prochains jours » du dashboard Cours (`schoolUpcomingItems`). Un devoir relié à un cours (`tasks.course_event`) garde son jour dans `due_date`, mis à jour par la relecture si le cours change de jour (`followCourseDatesStatement`). Le choix d'un cours passe par `CoursePicker` ; la page Emploi du temps montre la semaine Google (`CourseWeekGrid`), la semaine type saisie à la main n'est plus proposée.
- **Animations** : composants `m` de Motion et réglages de `src/ui/motion` (jamais le composant `motion` complet, `LazyMotion` est strict). Durées dans `presets.ts`, toujours via `transitionFor`, qui respecte « Réduire les animations ».

## Tester : les détails

- Dans le navigateur de test, `Ctrl+N` et `Ctrl+1…6` sont réservés par le navigateur ; dans l'app, `N` et `Ctrl+1…6` fonctionnent.
- Si l'interface affiche « Invalid hook call » après l'ajout d'une dépendance, recharger complètement la page (réoptimisation Vite).
- **Cockpit reste dans la zone de notification** : fermer sa fenêtre ne le quitte pas. Pour libérer le port 1420 ou relancer, le quitter par le clic droit sur son icône (« Cockpit (développement) » pour l'app de dev).
- **App de dev et app installée ensemble** : l'instance unique et le démarrage avec Windows n'existent que dans l'app installée.
- **Essai de lancement sans saisie** : `src-tauri/target/debug/cockpit.exe` (avec Vite sur le port 1420), éventuellement avec `--autostart` pour un démarrage caché. On peut vérifier ses fenêtres et envoyer un raccourci seul ; jamais de texte.
- Pendant un `npm run tauri dev`, modifier un fichier Rust recompile et relance l'app. `cargo test --lib` (dans `src-tauri`) teste les sauvegardes et la restauration.
